# browser-chain — 실행 절차

설계·실측 근거: `~/workspace/browser-chain-redesign-2026-11-24.md` (구 4레인 설계는 대체됨).

## 차단 회피와 대응 (전 사이트 공통, 2026-11-24 사용자 지시로 반영)

차단은 대개 출구 IP 자체가 아니라 **세션 유무와 요청 방식**에서 온다. 데이터센터 IP라는 이유만으로 "차단됨"으로 단정하지 않는다.

- **판정 주의**: 쿠키·JS 없는 L0 fetch 실패만으로 차단 판정을 내리지 않는다. 세션에 민감한 사이트는 실제 브라우저(세션 유지, 사람 속도)로 확인한 뒤에 판정한다. 같은 출구 IP라도 로그인 세션 + 사람 속도면 정상 통과하는 경우가 실측으로 확인돼 있다.
- **사전 회피**: 사람 속도를 지킨다. 연속 클릭, 새로고침 루프, 매크로식 반복, 짧은 시간 과다 요청은 차단의 실제 트리거이므로 하지 않는다. 민감 구간(결제·본인인증·대량 요청)은 한 번에 하나씩만 움직인다.
- **우회 금지**: VPN이나 프록시로 IP를 속이는 시도는 하지 않는다. 우회 IP 자체가 차단 사유가 되기도 하고 실익도 없다.
- **차단됐을 때**: 같은 방식으로 재시도를 반복해 상황을 악화시키지 않는다. 즉시 중단하고 사용자에게 알린다 — 어느 사이트에서, 어느 레인에서, 어떤 코드·현상으로 막혔는지. 대안 경로(예: 집 회선으로 나가는 브라우저)가 필요하면 그 판단을 사용자에게 올린다.
- **캐시 주의**: 라우팅 캐시의 실패 기록이 세션 없는 시도에서 나온 것이면, 그 도메인의 차단 여부를 캐시만으로 확정하지 않는다.

## 호출 (이것만 기억하면 된다)

```bash
META=~/workspace/muse-ultra-browser-build/meta-muse-ultra
$META/chain.sh read <url>   # 공개·읽기 전용 → L0 fetch → L1 Muse Ultra Browser
$META/chain.sh open <url>   # 렌더·JS·상호작용 필요 → L1
```

## 출력 계약

- 성공: 본문 + 최종 1줄, **exit 0**
  `%%CHAIN%% final lane=L0 status=ok code=- path=L0:ok elapsed_s=0.8`
- 실패: 최종 1줄만 (본문 없음), **exit 3** → L2(클라우드 브라우저)로 하강해 같은 URL을 가져온다
  `%%CHAIN%% final lane=L1 status=fail code=F-IP path=L0:F-IP>L1:F-IP elapsed_s=2.8`
- `path=`에 레인별 결과가 전부 들어 있다. 보고는 이 줄로 만든다 (아래 포맷).

## 분류 (호출 전 1회만)

| 상황 | 행동 |
|---|---|
| 공개 + 본문만 필요 | `chain.sh read` |
| 공개 + JS 렌더·화면 구조·클릭/입력 | `chain.sh open` 또는 L1 직접 호출 |
| 로그인 필요 (부동산뱅크·직방 등) | **체인 금지** → H255 agent-browser (사용자 규칙) |
| 결제·사용자 시청 | **체인 금지** → 클라우드 브라우저 라이브 |

## 실행 주체 판정 (직접 vs 서브에이전트 위임)

기본은 직접 실행이다. 아래 중 하나라도 해당하면 건별(또는 흐름별)로 서브에이전트에게 위임한다.
1. 독립 건 5건 이상이고 건당 예상 5초 이상 (합산 30초 이상)
2. L2 하강이 예상되는 독립 건 2건 이상
3. 예상 본문 합계 10KB 이상
4. 병행할 다른 작업이 있어 결과가 급하지 않을 때

근거 (2026-11-24 실측): 위임 고정 오버헤드(기동+지시 해석+보고)가 스폰당 12~16초라
손익분기 건수는 N > 15/t + 1 (t=건당 초) — L0 1.2초면 14건, 무거운 페이지 5초면 5건, L2 하강급 30초면 2건.
단일 L0 읽기를 위임하면 1.2초 일이 17초가 된다.

위임 시: 명령과 URL을 문자 그대로 지시에 넣고, 본문은 파일로 저장시켜
건당 1줄(`rc / bytes / %%CHAIN%% final 줄 / 본문 첫 줄`)만 보고받는다.
상태가 이어지는 상호작용 흐름은 쪼개지 말고 흐름 전체를 한 에이전트에게 맡긴다.
로그인·결제·라이브는 위임하지 않는다 (기존 분류 규칙 우선).

## 실패 코드 → 다음 행동

| 코드 | 의미 | 다음 행동 |
|---|---|---|
| F-IP | 403/429·차단 페이지 | 같은 레인 재시도 금지. exit 3이면 L2로 |
| F-BOT | 캡차·봇 판정 | L2로. L2도 막히면 중단·보고 |
| F-EMPTY | 추출 100자 미만 | chain이 레인 내 방식 변경 1회까지 자동 처리함. exit 3이면 L2로 |
| F-TIMEOUT | L0 20초 / L1 60초 초과 | L2로 |
| F-NET | 연결·프록시 오류 | L2로. 반복되면 직접 `run.sh`로 진단 (chain은 stderr를 버림) |
| F-AUTH | 로그인 벽 | 체인 종료 → H255 agent-browser |

공통: 동일 코드 2레인 연속이면 중단·보고. 전체 예산 5분 (chain.sh가 `CHAIN_BUDGET_S`, 기본 300초로 강제).
실패한 final 줄에는 `next_action=L2 handoff_completed=false`가 붙는다 — exit 3은 "L2 인계가 필요"라는 뜻이지 L2 실행 성공이 아니다.
라우팅 캐시는 레인별·코드별 만료다 (2026-11-27 개정): ok/F-IP/F-BOT 7일, F-AUTH 24시간, F-NET 60초, F-TIMEOUT 120초, 그 외 300초. F-EMPTY는 페이지 단위 현상이라 캐시에 넣지 않는다. `UB_ROUTECACHE=0`으로 캐시를 끌 수 있다.
