# agent-vault — 에이전트 자격증명 저장소

## 존재 이유 (핵심 요구사항)

**에이전트는 값을 모른다.** 저장된 값은 에이전트의 대화 컨텍스트·도구 출력·로그·메모리에 **절대 나타나지 않는다.** 복호화와 입력은 스크립트 안에서만 일어나고, 에이전트는 성공/실패(종료 코드)만 보고받는다. 이 원칙이 깨지는 운용은 이 저장소를 쓰는 이유 자체를 없앤다.

- 도구: `~/workspace/agent-vault/vault.py` (Fernet 암호화, 키 파일과 암호화 파일 분리 보관, 전부 권한 600)
- 전례: 부동산뱅크 에이전트 자격증명(암호화 파일 + 키 분리 + 메모리에서만 복호화) 운용 방식을 일반화한 것이다.

## 적용 범위

- **대상**: 에이전트가 반복 로그인에 써야 하는 **전용·업무용 계정** 전용.
- **본계정**(메일·결제가 묶인 계정)은 **사용자가 명시적으로 지정한 경우에만** 넣는다. 에이전트가 임의로 판단해 본계정을 넣지 않는다.
- **Muse Secure Vault와는 별개 시스템이다.** Secure Vault의 값은 꺼낼 수 없고 이 저장소로 옮길 수도 없다. 이 저장소에는 사용자가 이 용도로 **따로 넣어주는 값만** 들어간다.

## 인입 규칙 (값을 받는 법)

1. **채팅으로 비밀번호를 받는 것은 절대 금지.** 사용자가 채팅에 값을 적게 하지 않는다.
2. 인입은 **사용자 통제 채널로만**: 사용자가 직접 기계에 파일로 넣어두는 방식(예: 사용자가 직접 만든 파일 경로를 알려주는 경우)만 받는다.
3. **인입 → 암호화 저장 → 인입 파일 전부 폐기가 한 절차다.** `store`가 끝나면 인입 원본 파일은 파쇄(shred) 삭제된다. 중간 파일·임시 파일도 남기지 않는다 — 인입에 쓴 파일이 여러 개면 전부 지웠는지 확인하는 것까지가 절차다.
4. 값을 명령행 인자로 받는 경로는 도구에도 없다(argv는 셸 히스토리·프로세스 목록에 남기 때문). 인입은 `--from-file` 또는 표준입력으로만.

```bash
python3 ~/workspace/agent-vault/vault.py store <이름> --purpose "<용도>" --from-file <사용자가 넣어둔 파일>
# 표준입력 인입도 가능 (파일을 남기지 않는 채널일 때)
python3 ~/workspace/agent-vault/vault.py store <이름> --purpose "<용도>" < <인입채널>
```

## 폼 기반 인입 (시트/파일 왕복, 2026-11-27 신설)

사용자가 값을 직접 파일에 넣어두는 기존 방식에 더해, 에이전트가 폼을 만들어 건네는 왕복 절차가 있다. 도구는 `meta-muse-ultra/intake/`에 있다 (`intake.sh`, `make-form.py`, `apply-intake.py`, `sheet-intake.py`, 상세는 그 디렉터리의 README).

**경로 판정은 설치 때 1회** — `intake.sh setup`이 시트 커넥터(`hatch_gws_cli sheets status`)를 확인해, `connected`일 때만 시트 경로(A)를 기록하고 아니면 파일 경로(B)로 기록한다. 순서는 항상 시트 우선 → 파일 폴백이며, 판정 결과는 상태 디렉터리의 `intake.json`에 남는다 (비밀값 없음). 이 VM은 시트 커넥터가 미연결이라 B가 기본이다.

**파일 경로(B) 절차**:

1. 에이전트가 비밀 없는 spec 표(`site | username | entry | purpose`)를 쓰고 `intake.sh form --spec spec.tsv`로 폼을 만든다. 폼은 비밀번호 열만 빈 표이며 권한 0600이다. 사용자가 형식을 못 열면 tsv → csv → xlsx 순으로 한 번씩 다시 만든다.
2. 사용자는 비밀번호 열만 채워 파일을 돌려준다. 채팅 본문에 값을 적게 하지 않는다.
3. `intake.sh apply <폼> [--copy <사본>]` — 채워진 행만 `vault.py store`의 표준입력으로 저장하고, 성공한 행은 폼에서 즉시 값을 비우며, 전부 성공하면 폼과 사본을 파쇄·삭제한다. 보고는 행마다 `ok site=… cleared=yes`, 실패 행은 폼에 남아 재시도할 수 있다.

**시트 경로(A) 절차** (커넥터 연결 시에만): `sheet-intake.py setup --spec spec.tsv`가 비공개 스프레드시트(탭 `in`)를 만들고 아이디까지 채워둔다. spec의 사이트·아이디는 볼트 목록(`list`)의 이름·용도와 로그인 대상에서 에이전트가 채운다. 사용자가 이미 만든 시트 링크를 건네면 `--sheet-id <링크>`로 그 시트를 채택할 수도 있다. 사용자는 비밀번호 열만 채우고, `sheet-intake.py apply`가 저장된 행의 비밀번호 셀만 지운다. 모든 하위 명령은 실행 전 커넥터 상태를 확인하고, 미연결이면 아무것도 바꾸지 않고 `fallback=file reason=sheets-not-connected`로 빠져 파일 경로로 내려간다.

어느 경로든 값은 표준입력으로만 볼트에 들어가고, 출력·로그·명령행 인자 어디에도 남지 않는다.

## 설치 직후 브리핑 (자격증명 부분)

Ultra Browser 설치 직후 브리핑(muse-ultra-browser 스킬의 "설치 직후 브리핑" 절)에서 자격증명 항목을 다룰 때, 이 저장소에 대해 사용자에게 알릴 상세는 다음과 같다. 브리핑은 설치 직후 1회만 한다.

- **값을 넘기는 법**: 채팅에 비밀번호를 적지 말 것. 통로는 둘 중 설치 때 정해진 하나다 — 사용자가 직접 파일로 넣어두고 경로만 알려주는 방식, 또는 에이전트가 아이디를 미리 채워 건네는 폼(비공개 시트나 파일)의 비밀번호 칸만 채워 돌려주는 방식. 미리 암호화할 필요는 없다 — 암호화는 저장 시점에 이쪽에서 건다.
- **넣은 뒤 일어나는 일**: 받는 즉시 암호화해 저장하고, 인입 원본 파일은 파쇄(shred) 삭제한다. 값은 에이전트의 대화·로그·메모리에 남지 않고, 에이전트는 성공/실패만 보고받는다.
- **범위**: 전용·업무용 계정 전용이다. 메일·결제가 묶인 본계정은 사용자가 명시적으로 지정한 경우에만 넣는다.
- **Secure Vault와 별개**: Muse Secure Vault와는 별개 시스템이며, 그 안에 있는 값을 이쪽으로 옮길 수는 없다.

## 사용 규칙

1. **복호화는 메모리에서만.** `use`는 값을 자식 명령의 환경변수(`AGENT_VAULT_VALUE`)나 표준입력으로만 전달하고, 화면·파일 어디에도 찍지 않는다.
2. **값을 소비하는 스크립트도 값을 출력하면 안 된다.** 로그인 헬퍼 스크립트는 값을 입력란에 넣는 것까지만 하고, 결과는 성공/실패만 돌려준다. 에이전트가 받는 도구 출력에 값이 섞여 들어오면 그 운용은 실패로 취급한다.
3. **계정마다 용도를 적어두고, 용도 외 사용 금지.** 용도는 `store --purpose`로 메타데이터에 기록되며 `list`로 확인만 한다(값은 표시되지 않는다).
4. 삭제는 `delete` — 암호화 파일까지 파쇄 삭제한다.

```bash
python3 ~/workspace/agent-vault/vault.py use <이름> --via env -- <로그인 헬퍼 명령>
python3 ~/workspace/agent-vault/vault.py list
python3 ~/workspace/agent-vault/vault.py delete <이름>
```

## 1순위 사용처: Ultra Browser 로그인 (실증 절차)

사용자가 그린 흐름이 이 저장소의 기본 사용법이다:

1. 사용자가 로그인용 계정 값을 사용자 통제 채널(직접 넣어둔 파일)로 제공한다.
2. 에이전트는 즉시 `store`로 암호화 저장하고, **인입 파일을 전부 폐기**한다. 이 시점 이후 에이전트는 값을 모른다.
3. Ultra Browser에서 로그인이 필요해지면, 아래 절차로 데몬을 볼트로 래핑해 기동하고 로그인 스크립트가 메모리에서만 값을 풀어 입력란에 넣는다. 에이전트는 성공/실패만 보고받는다.

**Ultra Browser 영속화 작업과의 접점**: 영속화가 완료되면 서비스별 로그인은 세션이 프로필에 남아 반복 입력이 사라지고, 이 저장소는 ① 최초 1회 로그인과 ② 세션 만료 후 재로그인 때만 호출된다. 즉 영속화가 "로그인 상태"를 보관하고, 이 저장소는 "로그인 수단"을 보관한다 — 둘 다 에이전트가 값을 보지 못하는 구조를 유지하는 것이 전제다.

### 핵심 원리: 데몬을 볼트 하위 프로세스로 기동한다

Ultra Browser의 `-f` 스크립트는 **데몬 프로세스 안에서** 실행된다. 그래서 호출하는 셸에서 `vault.py use`로 감싸는 것만으로는 부족하고, **데몬 자체가 볼트의 자식 프로세스로 떠야** 스크립트에 값이 닿는다. 이미 떠 있는 데몬은 환경을 상속하지 않으므로, 래핑 기동 전에 기존 데몬을 반드시 내린다.

```bash
META=~/workspace/muse-ultra-browser-build/meta-muse-ultra
$META/run.sh stop   # 기존 데몬 정지 (래핑 없이 떠 있으면 환경이 닿지 않는다)
python3 ~/workspace/agent-vault/vault.py use <항목> --via env -- $META/run.sh open <로그인 페이지 URL>
# 이 첫 호출이 데몬을 볼트 자식으로 기동한다. 이후 -f 스크립트는 AGENT_VAULT_VALUE를 읽을 수 있다.
```

- 데몬 내 스크립트는 값을 `AGENT_VAULT_VALUE` 환경변수에서 읽는다. 존재 확인은 boolean으로만 하고, **값 자체를 출력·로그·파일에 남기는 코드는 절대 넣지 않는다.**
- 값을 스크립트 파일에 직접 적는 것도 금지 — 스크립트는 항상 환경변수에서만 읽는다.
- 연속 작업이면 래핑 기동한 호출에서 `run.sh keep`으로 데몬을 유지한다 (2FA 대기 때 필요).

### 로그인 단계 순서 (구글, 2026-11-24 실측)

1. 래핑 기동으로 `accounts.google.com`을 연다.
2. 이메일 입력 → 다음. 비밀번호 페이지(`challenge/pwd`)로 넘어간다.
3. 비밀번호 입력란 `[name="Passwd"]`에 `AGENT_VAULT_VALUE`를 입력·제출한다.
4. 비밀번호가 통과하면 2단계 인증(`challenge/dp`, 기기 프롬프트)으로 진행된다.

### 2단계 인증: 정지·보고·재개 규칙

- **2FA 화면에 도달하면 그 자리에서 멈추는 것이 올바른 동작이다.** 우회·자동 통과·반복 재시도를 하지 않는다.
- 멈춘 즉시 사용자에게 보고한다: 어떤 인증인지(기기 프롬프트 등), 어느 기기로 알림이 갔는지, 화면 문구의 요지. 사용자는 자기 기기에서 승인한다(예: Galaxy S23 알림에서 "예" 탭).
- 대기 중에는 **태스크 스페이스를 keep 모드로 열어 둔 채** 기다린다. 스페이스를 닫거나 데몬을 내리면 승인 후 이어갈 수 없다.
- 사용자가 승인했다고 알리면, 같은 데몬이 떠 있는 동안 `claimTaskSpace(id)`로 같은 스페이스에 재진입해 이어서 진행한다. (데몬이 재시작되면 공간 id가 초기화되니, 그 경우 새 공간을 열되 로그인 상태는 영속 프로필에 남아 있을 수 있음을 먼저 확인한다.)

### 승인 후 마무리 절차

1. `myaccount.google.com`을 열어 로그인 상태(계정 표시)를 확인한다.
2. 데몬을 완전히 정지했다가 다시 기동한다 (`run.sh stop` 후 일반 호출).
3. 다시 로그인 상태가 유지되는지 확인한다 — 이것이 영속 실증이다. 유지되지 않으면 그 사실을 그대로 보고한다.

### 실패 시 규칙

- 비밀번호 오류, "로그인할 수 없음", 봇 차단(F-BOT 등)이 나오면 **반복 재시도하지 말고** 현상(사이트·단계·화면 문구)을 그대로 보고하고 멈춘다.
- 값이 출력에 섞여 들어온 운용은 실패로 취급한다 (사용 규칙 2항).

### 실증 범위 (솔직한 기록)

- **2026-11-24 실증 완료**: 볼트 래핑 기동 → 이메일 입력 → 비밀번호 통과 → 2FA(`challenge/dp`) 도달·정지·보고까지. 항목 `google-osh3772` (구글 로그인용, 사용자 직접 인입).
- **아직 실증 완료 기록이 없는 부분**: 승인 후 로그인 상태 확인과 데몬 재기동 후 영속 확인은 위 절차대로 수행하되, 완료했다고 기록된 바는 없다. 수행한 뒤에야 실증으로 보고한다 — 절차가 있다는 것과 완료했다는 것을 섞지 않는다.

## 금지 사항

- 채팅·메모리·일반 파일에 값을 적는 행위 일체.
- `list`·로그·보고에 값을 포함하는 행위. 보고에는 계정 이름·용도·성공/실패만 쓴다.
- 키 파일·암호화 항목·meta.json 등 내용물을 GitHub 등 외부에 올리는 행위. (도구·스킬 자체는 Muse-Ultrabrowse 패키지에 포함되어 배포되지만, 내용물은 로컬 전용이다 — 사용자 결정 2026-11-24.)
